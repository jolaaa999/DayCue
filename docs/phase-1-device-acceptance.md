# DayCue 第一阶段：真机验收清单

本清单用于在**真实 iPhone** 上逐条验证行为。所有条目默认状态是 **未验证**，
只有在设备上真实执行并观察到预期结果后，才能改成「已通过」并记录证据。

> **不要用单元测试代替本清单。** DayCueCore 的测试能证明状态机与数据库行为，
> 但证明不了 EventKit 真的写了、麦克风真的录了、Vision 真的认出了字。
> 用 mock 通过 EventKit 验收，等于没有验收。

## 0. 前置

| 项 | 要求 |
|---|---|
| 设备 | iPhone，iOS 17.0 或更高 |
| 后端 | Mac 上运行 `daycued`，真机通过局域网 IP 访问（见 `apps/ios/README.md` 第 3 节） |
| 清单 | 先在系统「提醒事项」里建两个清单：`DayCue 测试`（可写）、以及任意一个已有的 |
| 网络 | 第一次跑通闭环时保持联网；离线用例单独做 |
| 记录方式 | 每完成一条，填写「实际结果」和截图/录屏文件名 |

判定用语统一为：**通过 / 失败 / 阻塞**（阻塞要写清卡在哪一步）。

### 执行优先顺序

按下面的顺序做，前面的失败会污染后面的结论：

1. 正常写入一条提醒（第 5 节）。
2. 故障注入：外部成功、本地未记回执；重启后仍只有一条且恢复绑定（第 6.2 节）。
3. 查询失败或权限不足时**不得**自动新建（第 4.4 节）。
4. 在中断恢复场景下，检查**已完成项目**与**跨清单移动项目**是否被正确查重（第 4.4 节）。
5. 日期型任务**无 EKAlarm、无本地通知**（第 5 节）。
6. 用户修改与旧解析响应并发时，过期候选不能被确认（第 3 节）。

> **不要只对已经 `written` 的任务点「重试」来证明查重有效。**
> 那种情况下状态机可能直接跳过查询，等于什么都没验。
> 验收必须真的走到**需要恢复与查重**的路径上（第 4.4、6.2 节）。
「看起来没问题」不算通过。

## 1. 文字：拆分笔记与多个任务

**对应验收项 1、2**

### 1.0 先说清楚：fixture 模式支持哪些输入

模拟供应商**不是**"能识别任何输入"，它只认一个样例：

| 输入 | fixture 返回 |
|---|---|
| **含 "PV" 字样**（如本节样例句） | 预设的 1 笔记 + 2 任务拆分 |
| 其它任意输入 | **空结果 + 警告**「模拟结果：输入未命中预设样例，未做任何结构化拆分」 |

因此：

- 在 fixture 模式下**不要**随手输入一句别的话，再把它当成"AI 没识别出来"——那只是没命中样例。
- 任意新输入的**识别质量**必须接**真实供应商**验证，固定响应不能作为通过依据。
  分层说明见 [phase-1-acceptance.md 第 6 节](phase-1-acceptance.md)。

### 1A 当前时间录入（在 App 里做）

**期望日期按执行当天推算，不要照抄下面的示例日期。**

1. 打开「记录」标签，在文本框输入：
   `今天操作系统讲了 PV 操作，我还是没理解，明晚八点提醒我复习，周五之前交实验报告。`
2. 点「保存这条文字记录」。

预期：
- [ ] 立刻出现「已保存到本机，正在解析。」——**在网络请求之前**就已经是"已保存"。
- [ ] 随后进入解析结果页，**恰好 3 条候选**。
- [ ] 第 1 条类型是**笔记**（不是任务），标题关于 PV 操作。
- [ ] 第 2 条是任务「复习操作系统 PV 操作」，截止 = **执行当天的次日 20:00**（设备本地时区），并带提醒时刻。
- [ ] 第 3 条是任务「交实验报告」，截止日 = **执行当天所在周的周五**，且明确显示**尚未设置提醒时间**。
- [ ] 每条候选都能看到**原文依据**。
- [ ] 因为后端跑在模拟模式，页面上有**「模拟结果」**标记。

> 为什么这里是相对的：时间解析用的是**这条记录的真实录入时刻**，
> 所以「明晚八点」永远等于"录入次日的 20:00"，会跟着执行日期走。
> 这一条能验证解析链路，但验证不了识别质量。

### 1B 固定 fixture（绝对日期，可复现）

这一条**不经过 App 与设备**，目的是拿到不随执行日期变化的**绝对**预期值。

## 2. 笔记与任务分开验收

**对应验收项 1、2。笔记不是任务，必须分开算。**

### 2.0 先说清楚笔记存在哪里

笔记**只有一处落点**：这条记录（capture）在本地 SQLite 里的解析结果
`proposal.payload_json`，也就是后端返回的原始 JSON。

- 它**不是**一条 `task` 行，所以不会出现在今天页，也不计入任务数。
- 它**不会**写进苹果提醒事项。
- 第一阶段「记忆」页是空态，所以除了「这条记录」本身，笔记没有第二个浏览入口。
  这不是缺陷，是第一阶段的范围决定，但验收时必须知道，否则会把「找不到笔记」
  误判成「笔记丢了」。

### 2.1 1 条笔记 + 2 条任务

1. 输入 `今天操作系统讲了 PV 操作，我还是没理解，明晚八点提醒我复习，周五之前交实验报告。`
2. 在预览页**不要动任何勾选**，直接确认。

预期：
- [ ] 预览页显示 **3 条候选**：1 条类型为「笔记」，2 条类型为「任务」。
- [ ] 确认后提示是「**已创建 2 条任务**」——是 2 不是 3。
- [ ] 今天页出现 **2 条**任务，且**没有**任何一条是那句 PV 笔记。
- [ ] 提示里另有「**1 条笔记只保存在本机这条记录里**」的字样。
- [ ] 苹果提醒事项里**没有**那条笔记。

### 2.2 取消其中一条任务

3. 重新走一遍同样的输入，这次**取消勾选**第 3 条（「交实验报告」）。
4. 确认。

预期：
- [ ] 提示是「**已创建 1 条任务**」。
- [ ] 提示仍然说「**1 条笔记**」——取消任务**不影响**笔记计数。
- [ ] 今天页只多出 **1 条**任务。
- [ ] 被取消的那条任务**没有**被创建，苹果提醒事项里也没有它。

### 2.3 反向操作

5. 把笔记那条的类型从「笔记」改成「任务」，确认。

预期：
- [ ] 这一次提示是「已创建 2 条任务」，且**不再**出现笔记计数。
- [ ] 说明「笔记不会被算成任务、任务也不靠类型猜」这条规则在两个方向都成立。

实际结果：＿＿＿　证据文件：＿＿＿

## 4. 提醒事项权限：授权 / 拒绝 / 撤销 / 恢复

**对应验收项 5**

### 4.1 首次拒绝

1. 全新安装（或先「设置 → 通用 → 传输或还原 → 还原位置与隐私」）。
2. 设置页点「请求提醒事项权限」，在系统弹窗选**不允许**。
3. 回到「记录」，输入 `明天下午两点交作业` 并确认创建。

预期：
- [ ] 任务**出现在今天页**，状态标签是「**等待写入苹果提醒事项**」。
- [ ] **不是**「写入失败」，也**不是**「已写入」。
- [ ] 任务可正常完成、撤销、编辑。

### 4.2 事后授权并重试

4. 到系统设置里把 DayCue 的提醒事项权限改成**完全访问**。
5. 回到 DayCue（切后台再切回），在今天页对该任务点「重试写入」。

预期：
- [ ] 状态变为「**已写入苹果提醒事项**」。
- [ ] 系统提醒事项里出现该条，且**只有一条**。

### 4.3 撤销权限

6. 到系统设置把权限改回**不允许**。
7. 回到 DayCue，创建一条新任务。

预期：
- [ ] 新任务状态是「等待写入」，任务仍在 App。
- [ ] 已经写入过的旧任务**不因此变成失败**（它们确实写过了）。

### 4.4 查重无法给出结论时的行为

查重必须区分「确实没有」和「查不了」。只有前者允许继续创建。

构造"查不了"最直接的办法是**在写入过程中撤销权限**：

1. 先在设置页确认有完整访问权限，且选好了可写清单。
2. 打开「设置 → DayCue → 提醒事项」，**停在那一页不要退出**。
3. 回到 DayCue，创建一条新任务；在它开始写入的瞬间切到系统设置，把权限改成**不允许**。
4. 回到 DayCue。

预期（任一分支都算通过，但**必须**落在下面之一，绝不能是"又建了一条"）：
- [ ] 状态是「**等待写入苹果提醒事项**」（等授权），或
- [ ] 状态是「**需要对账**」并给出「无法确认…」的说明。

绝不能出现：
- [ ] 状态显示「已写入」而苹果侧其实没有。
- [ ] 苹果侧出现两条同名任务。

5. 到苹果提醒事项里把某条任务的**复选框勾掉**（标记为已完成），
   然后在 DayCue 里对同一任务点「重试写入」。

预期：
- [ ] **不会**新建第二条。已完成项也必须在查重范围内。
- [ ] 如果确实新建了第二条，说明查重漏了已完成范围，属于**必须修复**的缺陷。

6. 把一个已经写入过的任务在苹果侧**移动到另一个清单**，再点「重试写入」。

预期：
- [ ] 不会新建第二条（查重按任务标识而不是按清单）。

实际结果：＿＿＿　证据文件：＿＿＿

## 5. 真实写入：清单、截止日期与提醒时间

**对应验收项 7**

前置：设置页选中 `DayCue 测试` 作为默认清单。

1. 记录 `明晚八点提醒我复习 PV`，确认创建。
2. 打开系统「提醒事项」App，找到 `DayCue 测试` 清单。

预期：
- [ ] 清单里出现该条，标题正确。
- [ ] **到期时间**是明天 20:00（不是今天、不是 00:00）。
- [ ] 该条带**提醒时间** 20:00。
- [ ] 备注里含 `DayCue 任务 ID: <uuid>`。
- [ ] 同时**没有**收到 DayCue 的本地通知（提醒已交给苹果提醒事项，不能双重提醒）。

3. 记录 `周五之前交实验报告`，确认创建。

预期：
- [ ] 该条是**日期型**：只设到**日期**，**没有**被补成 00:00 或某个具体时刻。
- [ ] 该条**没有**提醒时间。
- [ ] 该条**没有**闹钟（EKAlarm）。
- [ ] DayCue **不会**为它安排任何本地通知。
  「周五之前」只说了一个截止日，用户没有指定几点提醒，也没有授权任何默认提醒规则。
  这时候自作主张补一个提醒时刻是**编造用户意图**——只保存截止日期才是对的。
  验证方法：确认后等一会儿，设置页的通知列表里**不应**出现这条任务的待发通知；
  到当天也不会收到任何本地提醒。

> 只有当候选**确实带了提醒时刻**（例如「明晚八点提醒我」）时，才轮到"没有写进苹果提醒事项
> 就用本地通知兜底"。日期型截止任务不属于这种情况。

4. 在 DayCue 里把任务标记完成。

预期：
- [ ] 本地状态变为已完成。
- [ ] **不**声称已同步到苹果侧（第一阶段不做双向同步）。

实际结果：＿＿＿　证据文件：＿＿＿

## 6. 重复操作、失败重试与撤销

**对应验收项 6**

### 6.1 重复点按

1. 对同一条已写入的任务，快速**连点 5 次**「重试写入」。

预期：
- [ ] 系统提醒事项里**始终只有一条**。
- [ ] 界面出现「正在写入……请稍候」之类的提示，而不是并发写两次。

### 6.2 可复现的中断测试（故障注入，必做）

**这是唯一能证明"外部已写入、本地回执未落库"窗口被正确处理的方法。**

窗口只有几十毫秒，人工强杀基本不可能稳定命中，所以本版提供了仅 Debug 的注入点：

1. 确认当前是 **Debug 构建**。
2. 到「设置」页最下方「调试（仅 Debug 构建）」分区，打开
   **「故障注入：外部写入后立即中断」**。
3. 在「记录」页输入 `明天下午两点交作业`，确认创建。
   此时「苹果提醒事项写入成功」之后会**立刻退出进程**——
   本地绑定与回执**尚未落库**。
4. 确认 App 确实退出了。**先别急着重开**，先确认开关已经被消费：
   注入点是**一次性**的，触发时会先把开关关掉再退出。
5. 再次打开 App。

预期：
- [ ] 重启时恢复流程会跑一次（今天页短暂出现该任务）。
- [ ] 苹果提醒事项里这条任务**始终只有一条**（不是两条）。
- [ ] 本地任务状态最终是「**已写入苹果提醒事项**」，并带上了绑定。
- [ ] 今天页**不再**把这条任务列在「同步异常」里。
- [ ] 界面显示的写入状态与苹果侧的实际情况**一致**。

6. 重启后**不应再次退出**。打开「设置」→「调试（仅 Debug 构建）」，
   确认那个开关**已经自己变成关闭**——这是"只触发一次"在重启后成立的证据。
7. 想再复现一次时，手动把开关打开即可（属于重新装填）。

> 实测时把每一步的截图按顺序命名（例如 `6.2-1-注入退出.png`），
> 因为"只有一条"这个结论需要能对着外部清单数。

### 6.2b 普通强杀（补充，不作为关键窗口的证据）

6. 创建一个新任务并确认（应有权限，会立刻写入）。
7. 立即**强杀 App**（上滑关掉），再打开。

预期：
- [ ] 重启后不会因为恢复流程而**多出一条**。
- [ ] 状态与实际一致：写成功就是「已写入」，没写就是「等待写入」。

> **普通强杀不能替代 6.2。** 它多半会落在写入之前或之后，
> 命不中那个关键窗口，因此它只能证明"强杀本身不出错"，
> 不能证明"外部已写入、本地未落库"这一特定状态被正确处理。

### 6.3 失败重试

5. 把默认清单改成一个**不可写**的清单（例如「提醒事项」默认清单若不可写），或用系统限制构造写入失败。
6. 点重试。

预期：
- [ ] 状态显示**失败**，并给出原因。
- [ ] **绝不显示「已写入」**。
- [ ] 任务仍在 App，可改清单后重试成功。

### 6.4 撤销

7. 选一条**没在系统里改过**的任务，点「撤销」。

预期：
- [ ] 本地任务消失，系统提醒事项里对应条目**也被删除**。

实际结果：＿＿＿　证据文件：＿＿＿
